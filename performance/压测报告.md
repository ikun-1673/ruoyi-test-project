# 若依管理系统 登录接口 阶梯压测报告

> 测试日期：2026-09-23 ｜ 工具：Apache JMeter 5.6.3（CLI 模式）
> 被测对象：RuoYi-Vue3 v3.9.2 登录接口 `POST /login`

---

## 一、测试概述

对若依管理系统的登录接口执行 **4 档阶梯压测**（50 / 100 / 200 / 300 并发线程，每档持续 120 秒，
共发出 **29,595 次请求**），目的是定位系统吞吐量上限（拐点）、验证响应时间 SLA（< 2000ms）在多大并发下失守，
并通过 CPU 成本测量与资源监控定位瓶颈层级。

**核心结论**：TPS 在 50 线程即饱和于约 60 次/秒，之后并发增加只带来响应时间线性增长与 SLA 违约，
系统本身**零 HTTP 错误、未崩溃**；瓶颈在**应用层 CPU**，根因是 bcrypt 密码哈希（占单次登录 CPU 的 88%）。

---

## 三、测试场景与脚本设计

> 说明：脚本设计中的**预热步骤**是在冒烟测试（发现 JVM 冷启动导致前 5 个请求响应 967~3263ms）之后补充的规范流程。
> 本次四档实测早于该步骤落地，但经事后核验：**第 1 档（50 线程）未出现冷启动污染**（最小响应 203ms、错误率 0%、无 >2000ms 请求），
> 因此预热缺失未影响四档结论的成立。后续复现时建议保留预热步骤（见第十章）。

| 项 | 配置 |
|---|---|
| 接口 | `POST /login` |
| 请求头 | `Content-Type: application/json` |
| 请求体 | `{"username":"admin","password":"admin123"}` |
| 线程组 | 阶梯 50 / 100 / 200 / 300，Ramp-Up 10 秒，每档持续 120 秒 |
| 断言 1 | 响应体包含 `"code":200`（业务成功校验） |
| 断言 2 | 响应时间 < 2000 ms（SLA 校验） |
| 思考时间 | 无（极限容量测试，非真实用户行为模拟） |
| 超时设置 | 连接 10s / 响应 30s |
| 执行方式 | `jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=N -Jrampup=10 -Jduration=120 -l results/result_N.jtl -e -o reports/report_N` |

**脚本设计要点**：

1. **参数化线程组**：线程数/Ramp-Up/持续时间均通过 `${__P(threads,50)}` 形式由命令行注入，一个脚本跑完四档，避免手工改脚本引入误差
2. **双断言**：只配 HTTP 状态码断言是不够的——若依业务失败时 HTTP 仍返回 200（HTTP 200 + body `code:500`），必须断言响应体内容；响应时间断言用于量化 SLA 违约
3. **CLI 模式**：GUI 模式下监听器渲染会消耗压测机资源，导致测量结果失真
4. **无监听器**：脚本内不保留任何监听器，结果通过 `-l` 与 `-e -o` 事后生成

## 四、测试结果

### 4.1 四档指标总表

| 线程数 | 总请求数 | **TPS** | 平均 RT(ms) | 中位数(ms) | 90 线(ms) | **95 线(ms)** | 99 线(ms) | 最大(ms) | **错误率** |
|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| 50 | 7,102 | **59.00** | 812 | 877 | 1,073 | **1,126** | 1,225 | 1,484 | **0.00%** |
| 100 | 7,133 | **59.11** | 1,620 | 1,682 | 1,817 | **1,867** | 1,973 | 2,448 | **0.77%** |
| 200 | 7,684 | **63.24** | 3,023 | 3,073 | 3,603 | **3,679** | 3,816 | 4,198 | **94.98%** |
| 300 | 7,676 | **62.76** | 4,563 | 4,644 | 5,814 | **6,046** | 6,393 | 8,105 | **97.08%** |

### 4.2 错误构成分析（重要）

**四档压测的 HTTP 状态码 100% 为 200，无任何 HTTP 层错误。** 全部"失败"均为**响应时间超过 2 秒的断言失败**：

| 线程数 | 响应超时断言失败 | HTTP 错误 | 连接错误 | 说明 |
|:--:|:--:|:--:|:--:|:--:|
| 50 | 0 | 0 | 0 | 全部满足 SLA |
| 100 | 55 (0.77%) | 0 | 0 | 少量请求触及 SLA 边界 |
| 200 | 7,298 (94.98%) | 0 | 0 | 大规模 SLA 违约 |
| 300 | 7,452 (97.08%) | 0 | 0 | 几乎全部违约 |

> **结论**：系统在高并发下**没有崩溃、没有返回 5xx、没有连接拒绝**，只是服务能力被 CPU 限制后形成排队，导致响应时间劣化。这是一次"优雅降级"，而非故障。

### 4.3 趋势特征
```text
TPS:        59.00 → 59.11 → 63.24 → 62.76     平台期（不再随并发增长）
平均 RT:      812 → 1,620 → 3,023 → 4,563 ms   近似线性增长
95 线:      1,126 → 1,867 → 3,679 → 6,046 ms   跨越 2000ms SLA 边界
错误率:      0.00% → 0.77% → 94.98% → 97.08%   在 100→200 档之间突变
```

**Little's Law 验证**（TPS ≈ 并发数 ÷ 响应时间）：

| 线程数 | 线程数 ÷ 平均RT(秒) | 实测 TPS | 吻合度 |
|:--:|:--:|:--:|:--:|
| 50 | 50 ÷ 0.812 = 61.6 | 59.00 | ✅ |
| 100 | 100 ÷ 1.620 = 61.7 | 59.11 | ✅ |
| 200 | 200 ÷ 3.023 = 66.2 | 63.24 | ✅ |
| 300 | 300 ÷ 4.563 = 65.7 | 62.76 | ✅ |

实测数据完全符合排队论模型，说明测量结果可信。

## 五、拐点判定

| 拐点类型 | 判定位置 | 依据 |
|---|---|---|
| **吞吐量拐点**（TPS 饱和） | **50 线程** | TPS 从 5 线程的 16.3 升至 50 线程的 59.0 后再无增长，200/300 档仅提升至 63（+7%），并发增加不再产生有效吞吐 |
| **SLA 拐点**（响应时间失守） | **100~200 线程之间** | 95 线由 1,867ms（100 档）跃升至 3,679ms（200 档），跨越 2000ms 阈值；错误率同步由 0.77% 突增至 94.98% |
| **推荐并发上限** | **≤ 100 线程** | 该档 95 线 1,867ms < 2000ms，错误率 0.77%，仍满足 SLA |

## 六、瓶颈分析（量化证据链）

### 6.1 排除法定位瓶颈层级

| 检查项 | 观测数据 | 结论 |
|---|---|---|
| 内存 | 可用内存全程 3.0~3.7 GB（总 15.3GB） | ❌ 非内存瓶颈 |
| MySQL 连接 | 连接数稳定 18~21，活跃连接恒为 1 | ❌ 非数据库连接池瓶颈 |
| 网络 | 平均建连时间 0.0~0.1 ms（localhost） | ❌ 非网络瓶颈 |
| HTTP 错误 | 0 个（四档全部 200） | ❌ 非应用异常/崩溃 |
| **系统 CPU** | **50/100/200/300 档全程 98%~100%** | ✅ **CPU 瓶颈** |

### 6.2 CPU 成本量化测量

对后端进程做“单请求 CPU 成本”直接测量（预热 10 次后串行发压 50 次，读取进程 CPU 时间增量；
重复 3 次取区间；测量脚本见 `scripts/cpu_cost.py`）：

| 请求 | 单次 CPU 成本 | 单次墙钟时间 | 说明 |
|---|:--:|:--:|---|
| `POST /login` | **214 ms**（207~219） | 214 ms | 含 bcrypt 密码哈希、token 生成、登录日志写入 |
| `GET /system/user/list` | 25 ms（22~31） | 16 ms | 无 bcrypt，仅 token 校验 + SQL 查询 |
| **差值（bcrypt 与登录特有逻辑）** | **189 ms** | — | **占登录总 CPU 的 88%（86%~89%）** |

> 口径修正说明：初版测量预热仅 5 次，对照组仍处于 JIT 编译期（出现「CPU 68ms > 墙钟 17ms」异常），
> 导致 bcrypt 占比被低估为 63%；改为预热 10 次 + 串行 50 次 + 重复 3 次后修正为 88%，定性结论不变。

### 6.3 理论吞吐上限推算

```
单次登录 CPU 成本 = 214 ms（3 次独立测量：207 / 219 / 215 ms）
压测机逻辑核数   = 16

理论上限（后端独占全部 CPU）：16 核 ÷ 0.214s ≈ 75 TPS
实测峰值：63.24 TPS（200 线程）→ 达到理论独占上限的 84%
后端实际可用 CPU ≈ 63.24 × 0.214 ≈ 13.5 核（16 核的 84%）
                （其余被 JMeter 300 线程、MySQL、Redis、系统进程占用）

结论：实测峰值与理论推算属同一量级，且已达独占上限的 84%，
      说明登录接口吞吐确由 CPU 计算能力决定 → 瓶颈在应用层 CPU
```

### 6.4 根因

| 序号 | 根因 | 性质 |
|:--:|---|---|
| ① | **bcrypt 密码哈希是 CPU 密集型算法**（单次约 189ms CPU，占登录成本 88%） | **安全设计使然，非缺陷**——bcrypt 刻意设计为慢速哈希以抵抗暴力破解，代价是登录接口吞吐受 CPU 限制 |
| ② | **后端日志级别为 `debug`**，每次登录打印多条 MyBatis SQL 与业务日志，增加 CPU 与磁盘 IO 开销 | **可优化项**（生产环境不应开 debug） |
| ③ | **单机部署**：压测工具与被测系统、数据库争抢同一台机器的 CPU，后端实得约 84%（13.5/16 核，见 6.3） | **环境限制**，导致测量值偏悲观 |

## 七、结论与优化建议

### 7.1 结论

1. 登录接口在本机环境下**最大处理能力约 60 TPS**，瓶颈位于**应用层 CPU**（非数据库、非内存、非网络）
2. 系统在 300 并发下**未崩溃、无 5xx、无连接拒绝**，通过排队实现优雅降级，具备基本稳定性
3. 满足 2 秒 SLA 的并发上限为 **100 线程**（95 线 1,867ms，错误率 0.77%）
4. 当前吞吐上限主要受 bcrypt 安全设计与单机资源竞争影响；生产多机部署下容量将显著提升

### 7.2 优化建议

| 优先级 | 建议 | 预期收益 |
|:--:|---|---|
| 高 | 生产环境将 `logging.level.com.ruoyi` 由 `debug` 调整为 `info`/`warn` | 减少每条请求的日志序列化与磁盘 IO，降低 CPU 占用 |
| 高 | 压测在**独立压测机**上执行，压测机与被测系统分离 | 消除资源争抢，测量数据更接近真实容量 |
| 中 | 登录接口增加**限流/防暴力破解**（如按 IP/账号限流、失败次数锁定） | 保护 CPU 密集型接口不被恶意请求耗尽资源 |
| 中 | 对高频读取接口（如用户信息）引入缓存，减少重复计算与查库 | 降低单请求 CPU 成本 |
| 低 | 如业务允许，评估降低 bcrypt 强度（cost factor）或改用更高效的密码哈希方案 | 提升登录吞吐（需权衡安全性，不建议轻易调整） |
| 低 | 引入持续性能基线：将本脚本接入 CI，定期回归监控 TPS/95 线劣化趋势 | 及早发现性能退化 |

## 八、局限说明（诚实边界）

1. **单机环境**：JMeter、若依后端、MySQL、Redis 同机运行，CPU 相互争抢，测量值偏悲观，**不代表生产环境容量**
2. **未使用独立压测机与生产级数据量**：数据库为初始化数据，未覆盖大数据量下的查询性能
3. **监控工具限制（已定位并已于压测后修复）**：本次压测所用版本的进程级 CPU 采样存在缺陷（`psutil.Process(pid).cpu_percent(interval=None)` 每次新建对象缺少基线，导致进程 CPU 恒为 0），
   经核验 `monitor_20260923_105216.csv` 中的后端/JMeter/MySQL 进程 CPU 列确实全为 0；
   该缺陷已在压测**之后**用 `cpu_times()` 差值法修复并单独验证通过（实测后端占用 98%~113%），
   但**本次采集数据中不包含有效的进程级 CPU 明细**。因此瓶颈归因未依赖该列，而是改用两重替代证据：
   ① 系统级 CPU（99%~100% 打满）；② “单请求 CPU 成本”直接测量（214ms/次，bcrypt 占 88%）。
4. **单账号场景**：`admin` 单账号登录，未做 CSV 多账号参数化，未覆盖多用户并发下的数据隔离与锁竞争
5. **无网络延迟**：localhost 通信无真实网络链路耗时，弱网场景未覆盖
6. **日志级别非生产配置**：debug 级别放大了 CPU 开销，若为 info 级别吞吐应更高

## 十、复现方式

```bash
# 1. 前置：若依后端运行于 localhost:8080，验证码开关关闭
# 2. 预热（30 秒）—— 本次实测未执行，但为推荐步骤（消除 JVM 冷启动影响）
jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=10 -Jrampup=5 -Jduration=30 \
       -l results/warmup.jtl -e -o reports/warmup

# 3. 四档阶梯压测
jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=50  -Jrampup=10 -Jduration=120 -l results/result_50.jtl  -e -o reports/report_50
jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=100 -Jrampup=10 -Jduration=120 -l results/result_100.jtl -e -o reports/report_100
jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=200 -Jrampup=10 -Jduration=120 -l results/result_200.jtl -e -o reports/report_200
jmeter -n -t scripts/ruoyi_login.jmx -Jthreads=300 -Jrampup=10 -Jduration=120 -l results/result_300.jtl -e -o reports/report_300

# 4. 指标分析
python scripts/analyze_jtl.py

# 5. 单请求 CPU 成本测量（6.2 节证据，可选）
python scripts/cpu_cost.py
```
